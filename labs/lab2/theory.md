# Lab 2 — JDBC and PostgreSQL: Theory

## What changes after lab1?

The address book currently creates Java objects in memory. Closing the application loses that state. A database stores data independently of the application process and can serve multiple clients.

This lab introduces JDBC conceptually, explores PostgreSQL **directly with its command-line client**, and ends with two small JDBC console programs. The address-book GUI integration remains in lab3: we first isolate the database and Java API from interface events.

## Objects and relational data

A relational database organizes information into tables. A table has named, typed columns; each row stores one record. Our `persons` table represents contacts.

| SQL column | SQL type | Java representation in lab3 |
|---|---|---|
| `id` | `BIGINT` identity, primary key | `Long` |
| `first_name`, `last_name` | `VARCHAR(80)` | `String` |
| `street` | `VARCHAR(160)` | `String` |
| `postal_code` | `VARCHAR(20)` | `String` |
| `city` | `VARCHAR(100)` | `String` |
| `birthday` | `DATE` | `LocalDate` |

A **primary key** uniquely identifies a row. Names are unsuitable as IDs: two people can have the same name, and a name can change. PostgreSQL generates an identity value on insertion. Gaps in generated IDs are normal, including after rolled-back inserts; IDs are not row counts.

The postal code remains text so `00118` keeps its leading zeros. A birthday has no time of day, so `DATE`, not a timestamp, is appropriate.

`NOT NULL` rejects a missing value. It does not reject an empty string: our text columns also use `CHECK (btrim(column) <> '')`. The database protects these rules regardless of which client sends a command. Java validation will provide earlier, friendlier feedback in lab3.

## Networked and embedded databases

**PostgreSQL** runs as a separate server process. Clients connect through a network protocol, usually on TCP port `5432`. Running the server on your own machine is still a client/server architecture.

**SQLite** is an embedded library, usually backed by a local file; it does not require a separate server. Both are useful, but this course uses **PostgreSQL consistently**, first from `psql`, then from JDBC, and later behind an HTTP backend.

```text
Lab 2: terminal → psql client → PostgreSQL server → persistent storage
Lab 2: Java console examples → JDBC driver → PostgreSQL server → persistent storage
Lab 3: JavaFX → repository → JDBC driver → PostgreSQL server → persistent storage
```

`psql` is a client, not the database server. Closing it does not stop PostgreSQL.

## Containers, images, and volumes

Docker lets us run the same packaged PostgreSQL environment on different machines.

| Term | Meaning here |
|---|---|
| Image | The packaged PostgreSQL software, `postgres:17-alpine`. We select major version 17, not the moving `latest` tag. |
| Container | A running instance of that image. |
| Compose service | The `postgres` definition in `compose.yaml`. |
| Published port | Connects a host port to the container's port. |
| Named volume | Keeps PostgreSQL's data when its container is removed and recreated. |

The major-version tag still receives patch updates; exact image digests can pin a build more strictly. A persistent volume is **not a backup**.

In `127.0.0.1:5432:5432`, the host's loopback interface and port appear first; the container's port appears last. Inside the container, PostgreSQL still uses `5432` even if the published host port changes.

`POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD` initialize a **new empty data directory**. Changing them in Compose does not change credentials inside an existing database volume. Do not delete a volume just to troubleshoot a password error.

## SQL: the operations we need

SQL expresses operations on stored data. End SQL commands with a semicolon in `psql`.

* `CREATE TABLE`: define a table and its constraints.
* `INSERT`: create rows.
* `SELECT`: read rows, choosing columns and filtering with `WHERE`.
* `UPDATE`: change matching rows.
* `DELETE`: remove matching rows.

Without a `WHERE` clause, `UPDATE` and `DELETE` affect **every row**. Inspect the intended target with a `SELECT` before modifying it. Row order is not guaranteed without `ORDER BY`.

`RETURNING` is a PostgreSQL feature that returns values from a write, for example the ID generated by an `INSERT`. It will also simplify our JDBC implementation.

SQL strings use single quotes, for example `'Roma'`; double quotes quote identifiers. SQL `NULL` means a missing value, not the strings `'null'` or `''`.

## Transactions

A transaction groups work into a unit that can be committed or rolled back:

```sql
BEGIN;
UPDATE persons SET city = 'Modena' WHERE id = 123;
ROLLBACK;
```

This example makes no lasting city change, even if that ID exists. Replace `ROLLBACK` with `COMMIT` only when you intend to keep the changes. An explicit transaction that encounters an error must be rolled back before continuing.

By default, `psql` commits each successful statement outside an explicit transaction. JDBC connections also default to auto-commit. Atomicity applies to database work inside the transaction; it does not automatically include a GUI update or a later query on another connection.

## Where JDBC fits

**JDBC** is Java's standard API for database access, primarily in `java.sql` and `javax.sql`. The API defines interfaces; a **driver** provides database-specific implementations and protocol handling.

```text
Java code → JDBC API → PostgreSQL JDBC driver → PostgreSQL server
```

Java SE includes the JDBC API, but not the PostgreSQL driver. Maven downloads `org.postgresql:postgresql` for the small `jdbc-examples` project and later for lab3. With a modern JDBC driver, ordinary applications do not need a manual `Class.forName(...)` call to load it.

### Connection

A connection is a session with the database. A JDBC URL identifies the database location:

```text
jdbc:postgresql://localhost:5432/addressbook
```

User and password are supplied separately. `localhost` is correct for our Java application running on the host. An application running in another Compose container would normally use the service name `postgres` instead.

The following fragments introduce the API used by the complete console programs at the end of the tutorial. Those programs use a separate `names` table; the `persons` table is reserved for the address-book integration in lab3.

```java
try (Connection connection = DriverManager.getConnection(url, user, password)) {
    // Execute database operations here.
}
```

### PreparedStatement

A prepared statement separates SQL structure from parameter values:

```java
String sql = "SELECT id, first_name FROM persons WHERE city = ?";
try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setString(1, "Roma");
    // Execute the query here.
}
```

Parameters start at **1**, not 0. Do not concatenate user input or use `String.format` to build SQL values. Binding parameters correctly handles quotes and avoids treating a value as executable SQL. Parameters represent values, not arbitrary table names or SQL keywords.

### ResultSet

A result set is a cursor over returned rows. Initially it is positioned **before** the first row:

```java
try (ResultSet rows = statement.executeQuery()) {
    while (rows.next()) {
        long id = rows.getLong("id");
        String firstName = rows.getString("first_name");
    }
}
```

The ordinary result set is forward-only: use `next()`; do not assume backward navigation is supported. Read values while the result set and its statement/connection are still open, then return Java objects rather than a live cursor.

`executeQuery()` returns a result set. `executeUpdate()` returns an affected-row count for operations without a returned result set. With PostgreSQL's `INSERT ... RETURNING`, we use `executeQuery()` because the SQL returns rows despite being a write.

### Resource ownership and errors

Connections, statements, and result sets must be closed. Try-with-resources closes them in reverse declaration order even when an operation fails. `SQLException` contains diagnostic information; preserve it as the cause when translating it into an application exception.

A failed connection is not an empty address book. Do not hide failures by returning an empty list, and never respond to an arbitrary SQL error by dropping and recreating tables.

## What we postpone

Connection pools reuse physical connections; ORM tools automate parts of object–row mapping. Neither is required to understand one table and CRUD operations. We start with a short-lived connection per repository operation in lab3. We also postpone relationships between tables, joins, schema migration tools, and server-side application frameworks.
