# E5.1 — Exceptions and Propagation

An exception is an object used to report an exceptional outcome and transfer control to a matching handler. It is thrown during execution; a compilation error is a different kind of failure.

Put statement fragments inside `main` and method declarations inside a class. File examples need the relevant `java.io`, `java.nio.file`, `java.nio.charset`, or `java.util` imports. Blocks labeled as pseudocode explain control flow, not compilable Java.

## Why exceptions?
Imagine we need to write a method for loading a file in memory:

First approach (ignore error checking)
  * Short 
  * Readable 
  * Failure behavior is unspecified
  * **Not dependable**

```text
void loadFile()  {
  open file;
  determine file size;
  allocate memory;
  read file into memory;
  close file;
}

```

Second approach (error checking with [magic numbers](https://en.wikipedia.org/wiki/Magic_number_(programming)))
  * **Long**
  * **Obscure**
  * Can make failures explicit, if callers check the result
  * Cleanup still needs a policy

```text
int loadFile()  {
  open file;
  if (operationFailed) 
    return -1;
  
  determine file size; 
  if (operationFailed) 
    return -2;
  
  allocate memory; 
  if (operationFailed)
    return -3;
  
  read file into memory; 
  if (operationFailed)
    return -4;
  
  close file;
  if (operationFailed) 
    return -5;
  return 0;
}
```

Third approach (error checking with exceptions)
  * Reusable
  * Dependable
  * Readable

```text
void loadFile() {
  try {
      open file;
      determine file size;
      allocate memory; 
      read file into memory; 
      close file;
  } catch (fileOpenFailed) { 
      doSomething; 
  } catch(determineSizeFailed) {
    doSomething; 
  } catch (memoryAllocationFailed) { 
      doSomething; 
  } catch (readFailed) { 
      doSomething; 
  } catch (fileCloseFailed) { 
      doSomething; 
  }
}
```

These sketches illustrate reporting styles, not complete resource-safe implementations. Exceptions alone do not guarantee cleanup: owned resources must be closed on both success and failure, typically with try-with-resources. A named result type can also be appropriate for expected outcomes; error codes are not intrinsically wrong.

## Exceptions examples

### ArithmeticException

Suppose you are writing a program that reads two integers from the standard input and then outputs the result of the integer division of the first number by the second one. Look at the code below.

```java
import java.util.Scanner;

public class ArithmeticExceptionDemo {

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);

        int a = scanner.nextInt();
        int b = scanner.nextInt();
        
        // ArithmeticException here if b == 0
        IO.println(a / b);
        IO.println("finished");
    }
}
```

### NumberFormatException
Another situation to consider is when you are trying to convert a string into an integer number. If the string has an unsuitable format, the code will throw an exception.

The following program reads a line from the standard input and then outputs the number that follows it.

```java
import java.util.Scanner;

public class NumberFormatExceptionDemo {

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);
        String input = scanner.nextLine();

        // NumberFormatException here if user presses 121a
        int number = Integer.parseInt(input); 
        IO.println(number + 1);
    }
}
```

### ArrayIndexOutOfBoundsException
This is a fairly common exception that occurs while working with arrays. It is caused by attempting to access a non-existent element of the array.

```java
int[] array = { 1, 2, 3 }; // an array of ints

int n1 = array[2];  // n1 is 3
int n2 = array[3];  // ArrayIndexOutOfBoundsException
int n3 = array[-1]; // ArrayIndexOutOfBoundsException
```

### NullPointerException (NPE)
`null` is a reference value identifying no object, not an uninitialized local variable. Dereferencing it or implicitly unboxing it can cause `NullPointerException`. Choose an explicit absence policy; checking null is not always preferable to rejecting an invalid argument at a boundary.

```java
String someString = null; // a reference type can be null

int size = someString.length(); // NullPointerException (NPE)
```

## Hierarchy of exceptions
Exceptions are considered objects of special classes organized into a class hierarchy. The following picture illustrates the simplified hierarchy of exceptions:

```text
Throwable
├─ Error (unchecked)
│   ├─ OutOfMemoryError
│   ├─ StackOverflowError
│   └─ ... (many more)
└─ Exception
    ├─ RuntimeException (unchecked)
    │   ├─ NullPointerException
    │   ├─ ArrayIndexOutOfBoundsException
    │   ├─ ArithmeticException
    │   └─ ... (many more)
    ├─ IOException (checked)
    │   └─ FileNotFoundException
    ├─ SQLException (checked)
    └─ ... (other checked exception classes)
```

The `Throwable` class has several important subclasses:

* **`Error`** – represents serious problems in the JVM, e.g., `OutOfMemoryError`, `StackOverflowError`.
* **`Exception`** – represents application-level events that can be handled, e.g., `SQLException`, `IOException`.
* **`RuntimeException`** – a subclass of `Exception` representing **unchecked exceptions**, e.g., `ArithmeticException`, `NumberFormatException`, `NullPointerException`.


### Checked exceptions

Checked exceptions are exception types other than `RuntimeException` and its subclasses, and other than the `Error` branch. The compiler requires eligible checked failures to be caught or declared. Whether a failure is recoverable depends on the caller and context, not just on this classification.

With checked exceptions, the compiler forces the programmer to make a choice:
  
**Handle the exception** using a `try-catch` block:
```java
public static void displayFile() {
    try {
        String text = java.nio.file.Files.readString(java.nio.file.Path.of("file.txt"));
        IO.println(text);
    } catch (java.io.IOException e) {
        System.err.println("Cannot display file.txt: " + e.getMessage());
    }
}
```

**Propagate it** by declaring `throws` in the calling method.
```java
public static String readTextFromFile() throws java.io.IOException {
    return java.nio.file.Files.readString(java.nio.file.Path.of("file.txt"));
}
```

The first method is a console boundary that reports failure; the second leaves the decision to its caller. Returning an empty string after an I/O failure would make “empty file” indistinguishable from “could not read.” `Files.readString` owns and closes the underlying file operation.

### Unchecked Exceptions

Java introduced **unchecked exceptions** to address situations where **forcing the programmer to declare or handle every possible error would be cumbersome or unnecessary**.

```java
int[] array = { 1, 2, 3 }; // an array of ints

int n2 = array[3];  // ArrayIndexOutOfBoundsException is unchecked
```

`RuntimeException` and its subclasses are unchecked exceptions; `Error` and its subclasses are also unchecked throwable types. The compiler does not require catching or declaring them. That does not make them safe to ignore or imply that catching every `Throwable` is sensible.

```java
public static Long convertStringToLong(String str) {
    return Long.parseLong(str); // may throw NumberFormatException
}
```
This code **compiles successfully** without using the `throws` keyword because `NumberFormatException` is **unchecked**.

## Throwing exceptions
### The throw keyword
Any object of the  `Throwable`  class and all its subclasses can be thrown using the **throw** statement. 

```java
public class Main {
    public static void main(String[] args) {
        throw new RuntimeException("Something's bad.");
    }
}
```

With no handler in this example, the main thread terminates and the default uncaught-exception handling prints a stack trace:

```text
Exception in thread "main" java.lang.RuntimeException: Something's bad.
	at Main.main(Main.java:3)
```

### Throwing checked exceptions

```java
public static String readTextFromFile(String path) throws java.io.IOException {
    if (path.isBlank()) {
        throw new IllegalArgumentException("Blank path");
    }
    return java.nio.file.Files.readString(java.nio.file.Path.of(path));
}
```

The `throws` keyword following the method parameters is required since an `IOException` is a checked exception. Otherwise, the code won't compile.

If a method throws two or more checked exceptions, they must be separated by a comma in the declaration:

```text
public static void method() throws ExceptionType1, ExceptionType2, ExceptionType3 {
  // ...
}
```

If a method is declared as throwing an exception, it can also throw any subclass of the specified exception. In the example below, `FileNotFoundException` does not require a specific annotation because it is a subclass of `IOException`:

```java
public static String readLine(String filename) throws IOException {
  try (BufferedReader reader = new BufferedReader(new FileReader(filename))) {
    return reader.readLine(); // null at end-of-file; IOException on read failure
  }
}
```

### Throwing unchecked exceptions
The  `Account`  class contains the method called  `deposit`, that adds the specified amount to the current balance. If the amount is not positive or exceeds the limit, the method throws an `IllegalArgumentException`.

```java
class Account {

    private long balance = 0;

    public void deposit(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Incorrect sum " + amount);
        }

        if (amount >= 100_000_000L) {
            throw new IllegalArgumentException("Too large amount");
        }

        balance = Math.addExact(balance, amount);
    }
    
    // ...
}
```

If a method throws an unchecked exception such as `IllegalArgumentException`, the keyword `throws` is not required in the method declaration.

```java
public class AccountUtils {

  /**
   * Tries to deposit a given amount into the account.
   * Prints a message whether the deposit succeeded or failed.
   */
  public static void safeDeposit(Account account, long amount) {
    try {
      account.deposit(amount);
      IO.println("Deposit successful: " + amount);
    } catch (IllegalArgumentException e) {
      IO.println("Deposit failed: " + e.getMessage());
    }
  }

  public static void main(String[] args) {
    Account myAccount = new Account();

    // Test deposits
    safeDeposit(myAccount, 1000);          // valid
    safeDeposit(myAccount, -50);           // invalid: negative
    safeDeposit(myAccount, 200_000_000L);  // invalid: too large
  }
}
```

### When to throw an exception?
Technically, throwing an exception is a rather straightforward task. But the question is, when do you need to do this? The answer is not always obvious. 

Throw when the method cannot fulfill its contract and its API represents that failure with an exception. Broken preconditions are one case; external I/O failures, timeouts, and unavailable services can also occur with valid arguments.

* A date parser can throw `DateTimeParseException` for input that does not match its supported date format.
* A method reading a non-existing file throws a `FileNotFoundException`.

Choose a relevant standard type, such as `IllegalArgumentException`, rather than a generic `Exception` when possible. There is no standard `java.lang.InvalidArgumentException`. Expected absence may instead use a documented empty result or `Optional`; do not use exceptions as routine loop control.

## Testing expected exceptions

In [E2.8 — Unit Testing with JUnit](<E2.8 — Unit Testing with JUnit.md>), tests checked returned values. An exception can also be the expected outcome of a method's contract.

Save the following as `src/test/java/com/example/ParsingTest.java` in the practice project from E2.8:

```java
package com.example;

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.*;

class ParsingTest {
    @Test
    void parseIntRejectsNonNumericText() {
        assertThrows(NumberFormatException.class,
                () -> Integer.parseInt("12x"));
    }
}
```

* `NumberFormatException.class` identifies the expected exception type.
* `() -> Integer.parseInt("12x")` supplies an action for JUnit to execute. This is a lambda expression; its general form is covered in E7. For now, read it as “run this call when JUnit asks.”
* The assertion passes if that action throws the expected type or a subtype; it fails if nothing is thrown or a different type is thrown. Use `assertThrowsExactly` when the contract requires the exact type.

Keep the action narrow so an unrelated failing operation cannot satisfy the assertion. Do not catch and ignore the exception inside the test: the test must fail if the expected rejection does not occur. Test valid input with ordinary value assertions too.
