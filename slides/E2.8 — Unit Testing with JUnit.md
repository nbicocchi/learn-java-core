# E2.8 — Unit Testing with JUnit

## From output to automated checks

Compilation checks whether a program follows the language rules, not whether it meets its requirements. Printing a result and inspecting it manually is useful while exploring, but it is easy to overlook a wrong value or forget to repeat a check.

A **unit test** automatically checks a small unit of behavior, such as one method, against an expected result. A **test suite** is a set of tests that can be rerun after a change. A test that protects against the return of a previously fixed bug is a **regression test**.

Tests provide evidence for the cases they exercise, not proof that a program is correct for every input. Unit tests also do not replace integration tests between components or manual checks of a user interface.

## A small Maven project

The examples use **JUnit Jupiter**, the programming model used by the repository's JUnit tests. Create this independent practice project:

```text
testing-basics/
 ├─ pom.xml
 └─ src/
    ├─ main/java/com/example/Basics.java
    └─ test/java/com/example/BasicsTest.java
```

Use this complete `pom.xml`, with JDK 25 and Maven installed. The versions match the course's `deploy-cli` example; they are not a claim about the latest release.

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"

        <maven.compiler.release>25</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>

    <dependencies>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
```

* `test` scope makes JUnit available to test code, not to application code.
* The Jupiter dependency includes support for the parameterized tests used below.
* Maven Surefire discovers and runs the tests. Keep the conventional `BasicsTest` class name.

## Start with a contract

Before writing assertions, decide what the method promises:

| Method | Contract for this example |
|---|---|
| `clamp(value, min, max)` | Return `min` below the interval, `max` above it, otherwise `value`. Requires `min <= max`. |
| `isPalindrome(text)` | Compare characters exactly, including case and spaces. Empty and single-character strings are palindromes. Requires non-null text. |
| `reversedCopy(values)` | Return a new array in reverse order without changing the input. Requires a non-null array. |

Inputs outside these preconditions have no specified behavior here. Defining and testing explicit rejection with exceptions comes in E5.

Save this as `src/main/java/com/example/Basics.java`:

```java
package com.example;

public class Basics {
    public static int clamp(int value, int min, int max) {
        if (value < min) {
            return min;
        }
        if (value > max) {
            return max;
        }
        return value;
    }

    public static boolean isPalindrome(String text) {
        for (int left = 0, right = text.length() - 1; left < right; left++, right--) {
            if (text.charAt(left) != text.charAt(right)) {
                return false;
            }
        }
        return true;
    }

    public static int[] reversedCopy(int[] values) {
        int[] result = new int[values.length];
        for (int i = 0; i < values.length; i++) {
            result[i] = values[values.length - 1 - i];
        }
        return result;
    }
}
```

These methods return values rather than reading the keyboard or printing. Keeping computation separate from console interaction makes it easy to supply fixed inputs and check results.

## The first test: Arrange–Act–Assert

Save this as `src/test/java/com/example/BasicsTest.java`:

```java
package com.example;

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.*;

class BasicsTest {
    @Test
    void clampReturnsUpperBoundWhenValueIsTooLarge() {
        // Arrange: choose input and expected result
        int value = 12;
        int expected = 10;

        // Act: invoke the behavior under test
        int actual = Basics.clamp(value, 0, 10);

        // Assert: compare the result with the requirement
        assertEquals(expected, actual);
    }
}
```

* `@Test` marks a method for JUnit to run; it is an **annotation**, not a method call.
* A basic test method returns `void`, takes no arguments and is not `static`. The class and method do not need to be `public`.
* JUnit invokes the test; no `main` method is needed. Treat the test class as a container for now; class design comes in E3.
* `import static` lets us write `assertEquals(...)` instead of the fully qualified assertion name.
* Put the **expected** value first and the **actual** result second. Derive the expected result from the contract, not by copying the implementation.

From the `testing-basics` directory, run:

```bash
mvn test
```

Check that the summary reports **1 test**, with zero failures and errors. Reports are in `target/surefire-reports/`. A build that runs zero tests has not verified this behavior.

**Experiment:** change the expected value to `9` and rerun. Read the expected/actual diagnostic and locate the failing assertion. Restore `10` afterward. This checks that the test is really being executed.

## Assertions for different results

Add the following methods **inside the existing `BasicsTest` class**:

```java
@Test
void palindromeUsesExactCharacters() {
    assertTrue(Basics.isPalindrome("level"));
    assertFalse(Basics.isPalindrome("Level"));
}

@Test
void emptyAndSingleCharacterStringsArePalindromes() {
    assertTrue(Basics.isPalindrome(""));
    assertTrue(Basics.isPalindrome("x"));
}

@Test
void reversedCopyReversesContentsWithoutChangingInput() {
    int[] input = {2, 5, 8};

    int[] actual = Basics.reversedCopy(input);

    assertArrayEquals(new int[]{8, 5, 2}, actual);
    assertArrayEquals(new int[]{2, 5, 8}, input);
    assertNotSame(input, actual);
}

@Test
void reversedCopyHandlesEmptyAndSingleElementArrays() {
    assertArrayEquals(new int[]{}, Basics.reversedCopy(new int[]{}));
    assertArrayEquals(new int[]{7}, Basics.reversedCopy(new int[]{7}));
}

@Test
void floatingPointComparisonUsesATolerance() {
    double actual = 0.1 + 0.2;

    assertEquals(0.3, actual, 1.0e-12);
}
```

| Assertion | Purpose |
|---|---|
| `assertEquals(expected, actual)` | Compare values; for strings, compare contents rather than reference identity. |
| `assertTrue(condition)` / `assertFalse(condition)` | Check a boolean result. |
| `assertArrayEquals(expected, actual)` | Compare array contents, not just their references. |
| `assertNotSame(first, second)` | Check that two references identify different objects. |
| `assertEquals(expected, actual, delta)` | Compare floating-point values with an absolute tolerance appropriate to the requirement. |

JUnit assertions are not Java's `assert` statement: they do not require the JVM's `-ea` flag. A printed value alone does not make a test fail when the value is wrong.

Several assertions can describe one coherent behavior, such as returning a reversed copy without mutating the input. Avoid combining unrelated behaviors into one large test.

## Choosing cases and testing boundaries

For `clamp(value, 0, 10)`, choose inputs from distinct regions:

| Region | Input | Expected |
|---|---|---|
| Below the interval | `-1` | `0` |
| Lower boundary | `0` | `0` |
| Inside the interval | `5` | `5` |
| Upper boundary | `10` | `10` |
| Above the interval | `11` | `10` |

Also check an interval with equal bounds: `clamp(5, 3, 3)` must return `3`. For strings and arrays, consider empty, one-element, and multi-element inputs. Tests should distinguish plausible mistakes, not merely repeat one easy case.

### Parameterized tests

When the same behavior needs several input/expected pairs, use a parameterized test. Add these imports to `BasicsTest.java`:

```java
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
```

Add this method inside `BasicsTest`:

```java
@ParameterizedTest
@CsvSource({
        "-1, 0, 10, 0",
        "0, 0, 10, 0",
        "5, 0, 10, 5",
        "10, 0, 10, 10",
        "11, 0, 10, 10",
        "5, 3, 3, 3"
})
void clampHandlesRegionsAndBoundaries(int value, int min, int max, int expected) {
    assertEquals(expected, Basics.clamp(value, min, max));
}
```

Each CSV row supplies arguments for a separate invocation. Do not also add `@Test` to this method. With all examples included, `mvn test` should report **12 tests**: six ordinary tests and six parameterized invocations.

## A useful testing workflow

1. Write down the behavior and select representative inputs, including boundaries.
2. Add a test with a clear name describing the expected behavior.
3. Run it and inspect any failure; either the implementation or the test's expectation may be wrong.
4. Fix the problem, then rerun the whole suite to detect regressions.
5. Refactor while preserving the behavior checked by the tests.

Keep tests independent: do not rely on execution order or shared mutable data. Prefer fixed inputs to keyboard interaction, current time, or network access in these unit tests.

**Practice:** add tests for an even-length palindrome, a non-palindrome, an array with repeated values, and a negative interval for `clamp`. Then deliberately break the reverse-index calculation and check which tests detect the defect.
