# E2.6 — Java Wrapper Classes

Each primitive type has a corresponding **wrapper class**. Wrappers are immutable reference types, not alternative names for primitive types.

All examples target **Java 25 without preview features** and build on E2.1–E2.5: values, references, nulls, and string comparison.

* **Core:** understand boxing and unboxing, parse values, compare wrappers correctly, and recognize implicit null failures.
* **Note:** supporting details, optional on a first reading.
* **Reference:** type mappings and API guarantees to consult when needed.

Unless a complete class is shown, place statements inside `main`.

Wrappers are useful when:

* An API requires an object, such as a generic collection.
* Absence is represented by `null`, with an explicit policy for handling it.
* You need conversion methods or constants associated with a primitive type.

Prefer primitives for ordinary numeric computation when absence and an object-based API are not required.

**Reference — type mapping:**

| Primitive | Wrapper |
|---|---|
| `boolean` | `Boolean` |
| `byte` | `Byte` |
| `short` | `Short` |
| `char` | `Character` |
| `int` | `Integer` |
| `long` | `Long` |
| `float` | `Float` |
| `double` | `Double` |

## Boxing and unboxing

**Boxing** converts a primitive value to a corresponding wrapper reference. It does not necessarily allocate a fresh object.

**Unboxing** extracts the primitive value from a wrapper object.

```java
int primitive = 100;
Integer wrapped = Integer.valueOf(primitive);
int extracted = wrapped.intValue();
```

The compiler can insert these conversions automatically:

```java
Integer wrapped = 100; // Autoboxing
int extracted = wrapped; // Auto-unboxing
```

Use factories or autoboxing, not deprecated wrapper constructors such as `new Integer(...)`.

### Immutable object, reassignable variable

**Predict:** do both variables become `11`?

```java
Integer first = 10;
Integer second = first;
first++;
System.out.println(first);
System.out.println(second);
```

<details>
<summary>Check your prediction</summary>

The outputs are `11` and `10`. Incrementing unboxes, adds one, and boxes the result back into `first`. It does not mutate the old `Integer` object shared with `second`.

</details>

### Wrappers in collections

**Note — preview of E4.1:**

```java
java.util.List<Integer> scores = new java.util.ArrayList<>();
scores.add(10); // Boxing
int score = scores.get(0); // Unboxing
```

Generic type arguments must be reference types: `List<Integer>`, not `List<int>`. `int[]` is nevertheless a reference type: an array object whose components are primitive integers.

## Converting Strings to Primitive Types

```java
int count = Integer.parseInt("42");
double value = Double.parseDouble("3.14");
boolean enabled = Boolean.parseBoolean("true");
System.out.println(count);
System.out.println(value);
System.out.println(enabled);
```

`parseInt` returns an `int`; `Integer.valueOf("42")` returns an `Integer`. Choose the return type your API needs.

### Parsing is not validation of the whole requirement

```java
String supplied = " 42 ";
int count = Integer.parseInt(supplied.strip());
if (count < 0 || count > 100) {
    throw new IllegalArgumentException("Count must be between 0 and 100");
}
```

Here we explicitly accept surrounding whitespace and restrict the application range. `parseInt` alone would not establish that range.

**Reference — important differences:**

| Input or operation | Outcome |
|---|---|
| `Integer.parseInt("hello")` | `NumberFormatException` |
| `Integer.parseInt("2147483648")` | `NumberFormatException`: outside int range |
| `Integer.parseInt(" 42 ")` | `NumberFormatException`: no automatic trimming |
| `Double.parseDouble("NaN")` | `NaN`, not a parsing failure |
| `Boolean.parseBoolean("TRUE")` | `true` |
| `Boolean.parseBoolean("yes")` | `false`, not a parsing failure |
| `Boolean.parseBoolean(null)` | `false` |

**Review:** an assistant claims `Boolean.parseBoolean` validates that input is either `"true"` or `"false"`. Which input disproves that? If other input must be rejected, validate it explicitly before converting.

> **Note:** `Double.parseDouble` uses Java's numeric syntax, not locale-specific decimal separators. Successful parsing can produce non-finite values; use `Double.isFinite` if the requirement excludes them. Decimal overflow can produce infinity rather than `NumberFormatException`.

## Converting Primitive Types to Strings

```java
String count = Integer.toString(42);
String value = Double.toString(3.14);
String enabled = Boolean.toString(true);
String alternative = String.valueOf(42);
```

Conversion is not display formatting. For a fixed number of displayed fractional digits, use formatting as in E2.7.

> **Note:** converting a nullable reference through `String.valueOf(Object)` produces the text `"null"` when the reference is null. Decide whether that text is suitable rather than allowing it to leak into a user-facing message accidentally.

## Comparing wrappers

For two wrapper references, `==` checks identity, not numeric value. `equals` compares values **according to the wrapper's type-specific contract**.

```java
Integer first = Integer.valueOf("2000");
Integer second = Integer.valueOf("2000");
System.out.println(first == second); // Identity: do not rely on the result
System.out.println(first.equals(second)); // true
```

Do not infer value-comparison behavior from a particular JVM's allocation or caching choices.

### Caching

**Note — explaining identity, not choosing a comparison strategy:**

```java
Integer first = Integer.valueOf(100);
Integer second = Integer.valueOf(100);
System.out.println(first == second); // true: guaranteed valueOf cache range
```

`Integer.valueOf(int)` guarantees caching from **−128 to 127**, and may cache additional values. The language also guarantees shared identity for boxing certain small constant values. These guarantees should not be generalized into an identity rule for every wrapper expression.

**Core rule:** compare values using the intended value operation, not reference identity. The string-pool and wrapper-cache mechanisms are different; neither makes `==` a general content comparison.

### Same number, different wrapper type

```java
Integer integer = 42;
Long longValue = 42L;
System.out.println(integer.equals(longValue)); // false
```

`Integer.equals` requires another `Integer`, not merely a numerically equivalent `Number`. Normalize to an agreed numeric type when cross-type comparison is part of the requirement.

### Mixed primitive and wrapper comparison

```java
Integer wrapped = 2000;
int primitive = 2000;
System.out.println(wrapped == primitive); // true: numeric comparison after unboxing
```

The operand types matter: this is not a comparison between two wrapper references. If `wrapped` is null, the same expression fails during unboxing.

> **Note:** floating-point wrappers have additional equality rules: `Double.equals` treats NaN values as equal and distinguishes positive and negative zero. Do not assume its behavior is identical to primitive floating-point `==`.

## NPE when unboxing

Unboxing a null reference throws `NullPointerException`, even when no explicit unboxing method appears.

```java
Integer count = null;
// int value = count;       // NPE: assignment requires unboxing
// boolean empty = count == 0; // NPE: comparison requires unboxing
// count++;                // NPE: increment requires unboxing
```

**Predict:** does the following comparison merely return `false`?

```java
Boolean enabled = null;
if (enabled) {
    System.out.println("Enabled");
}
```

<details>
<summary>Check your prediction</summary>

No: evaluating the condition unboxes null and throws `NullPointerException` before either branch can run.

</details>

### Choose a policy for absence

```java
Boolean enabled = null;
boolean active = Boolean.TRUE.equals(enabled); // Explicit policy: null is not true

Integer count = null;
if (count != null && count > 0) {
    System.out.println("Positive count");
}
```

These examples treat absence as “not active” or skip processing. That is not always the right policy: a required missing value may need to be rejected instead. Do not silently replace every null with zero or false.

For equality of two possibly null references, `java.util.Objects.equals` avoids dereferencing null, but retains each wrapper's type-specific equality rules.

### Debugger activity

Assign a nullable `Integer` to an `int` local variable and run with an exception breakpoint for `NullPointerException`. Locate the source expression that requires unboxing. Explain why a line without an explicit method call can still throw the exception.

## Read, predict, verify

For code written manually or generated by an assistant, ask:

* Is this expression operating on primitives or references?
* Is boxing or unboxing happening implicitly?
* Is null valid here, and what policy handles it?
* Does parsing accept values the application must reject?
* Are equal-looking numbers actually the same wrapper type?

**Exit activity:** review `if (count == 0)` when `count` is an `Integer` returned by an external API. Supply a failing input and propose a correction based on an explicit absence policy.
