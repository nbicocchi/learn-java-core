# E3.8 — Java Enums and State Modelling

## Enums
An **enum** declares a finite set of named instances. It improves type checking and makes a closed vocabulary explicit. It does not automatically validate transitions between states, and enum references can still be null.

```java
public class Pizza {
    public enum PizzaStatus {
        NOT_ASSIGNED,
        ORDERED,
        READY,
        DELIVERED
    }
    private PizzaStatus status = PizzaStatus.NOT_ASSIGNED;
    
    public boolean isDeliverable() {
        return status == PizzaStatus.READY;
    }
}
```

## Values and transitions are different contracts

`PizzaStatus` restricts the possible values, but it does not encode which change is allowed next. For this example, suppose the required workflow is:

```text
NOT_ASSIGNED -> ORDERED -> READY -> DELIVERED
```

Add these operations **inside the preceding `Pizza` class**. Rejecting a transition before assignment leaves the old state intact. The enum remains a vocabulary; the object owns the transition rules.

```java
public void placeOrder() {
    if (status != PizzaStatus.NOT_ASSIGNED) {
        throw new IllegalStateException("Order already placed");
    }
    status = PizzaStatus.ORDERED;
}

public void markReady() {
    if (status != PizzaStatus.ORDERED) {
        throw new IllegalStateException("Pizza has not been ordered");
    }
    status = PizzaStatus.READY;
}

public void deliver() {
    if (status != PizzaStatus.READY) {
        throw new IllegalStateException("Pizza is not ready");
    }
    status = PizzaStatus.DELIVERED;
}
```

**Predict:** after `placeOrder()` and `markReady()`, what does `isDeliverable()` return? What if `deliver()` is called on a new pizza, or twice on the same pizza? The exception mechanism is developed in E5; here the important point is the preserved state invariant.
