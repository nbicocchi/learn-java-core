# E3.4 — Interfaces

All examples target **Java 25 without preview features**. Familiarity with classes, constructors, inheritance, and method overriding is assumed.

* **Core:** express a capability with an interface, share implementation when justified, and keep clients independent of concrete tools.
* **Note:** interface evolution and design trade-offs.
* **Reference:** multiple-interface rules and hierarchy diagrams.

The drawing examples evolve through alternative implementations. Compile each version separately. Use `import java.awt.Color;` for color and this small prerequisite type:

```java
record Curve(String description) {
    public String draw() {
        return description;
    }
}
```

The examples describe drawing using strings; they do not implement graphical rendering.

## Motivation

We aim to develop a drawing game. As an initial proof of concept, we will focus exclusively on pencil-based drawing, allowing users to create sketches using a variety of colors.

* The **Pencil** class provide methods to draw and change its color.
* The **Player** class can use a Pencil to perform drawing operations.

```mermaid
classDiagram
   class Pencil {
      - Color: color
      + Color getColor()
      + void setColor(Color c)
      + draw()
   }

    class Player {
        +draw(Pencil pencil)
    }

    Player --> Pencil
```

We implement everything, and it works like a charm. However, we get our next task. On top of drawing with a Pencil, we must support drawing with a Brush, as well.

No problem, we introduce the Brush class and the Player.draw(Brush) method:


```mermaid
classDiagram
   class Pencil { 
       - Color: color
       + Color getColor()
       + void setColor(Color c)
       + draw()
   }

   class Brush {
       - Color: color
       + Color getColor()
       + void setColor(Color c)
       + draw()
   }

    class Player {
        +draw(Pencil pencil)
        +draw(Brush brush)
    }

    Player --> Pencil
    Player --> Brush

```

So far, so good. But then we face the next task: adding more drawing tools.

We could repeat the same process we did with the Pencil and Brush. However, we start wondering: how many other tools might we need to support? 

**Limitations of This Approach:**

* **No Common Abstraction**: `Pencil` and `Brush` have no shared abstraction, meaning **we cannot treat all tools generically**.
* **Tight Coupling**: Supporting a new unrelated tool requires another overload or another client edit. A subclass of an already supported tool does not necessarily require a new overload, but the API still names concrete tool families.
* **Concrete dependencies**: the player knows each supported family instead of only the operation it needs. This is about dependency structure, not the order in which instructions execute.

## Using abstraction

We decide that we’ll create an abstract DrawingTool class, which will be the superclass of the Pencil, Brush and all future classes.

Also, this way, we’ll need a single draw(DrawingTool) method in the Player class:

```mermaid
classDiagram
    class DrawingTool {
        - Color: color
        + Color getColor()
        + void setColor(Color c)
        + draw()
    }

    class Pencil {
        + draw()
    }

    class Brush {
        + draw()
    }

    class Spray {
        + draw()
    }

    class Player {
        +draw(DrawingTool tool)
    }

    Pencil --|> DrawingTool
    Brush --|> DrawingTool
    Spray --|> DrawingTool
    Player --> DrawingTool
```

By using **abstractions**, OOP separates the *what* (abstract behavior) from the *how* (concrete implementations).

* We can express the **capabilities** of all tools without tying the application to a concrete implementation.
* New tools can be added without modifying existing code, improving **extensibility** and **maintainability**.
* The player depends on a stable contract. Runtime calls still have an order; abstraction changes what the client must know, not the need to execute operations.

## Interfaces
An interface is a **reference type distinct from a class**. It defines a contract that multiple classes can implement without sharing an implementation superclass.

* Interfaces cannot have constructors, as they cannot be instantiated.
* A method declared without a body, `private`, `static`, or `default` is implicitly `public abstract`.
* Interfaces can also declare default, static, and private methods with bodies, as shown below. Fields are implicitly `public static final`; there is no per-instance interface state.
* Other classes can **implement** an interface by providing concrete implementations for its abstract methods.

```mermaid
classDiagram
   class DrawingTool {
      <<interface>>
      + String draw(Curve curve)
      + Color getColor()
      + void setColor(Color color)
   }

   class Pencil {
      - Color color
      + Pencil(Color color)
      + Color getColor()
      + void setColor(Color color)
      + String draw(Curve curve)
   }

   class Brush {
      - Color color
      + Brush(Color color)
      + Color getColor()
      + void setColor(Color color)
      + String draw(Curve curve)
   }

   class Player {
      +draw(DrawingTool tool)
   }

   Player --> DrawingTool
   DrawingTool <|.. Pencil
   DrawingTool <|.. Brush
```

```java
interface DrawingTool {
    String draw(Curve curve);
    Color getColor();
    void setColor(Color color);
}
```

```java
class Pencil implements DrawingTool {
    Color color;
    
    public Pencil(Color color) {
        this.color = color;
    }
    
    public Color getColor() {
        return color;
    }
    
    public void setColor(Color color) {
        this.color = color;
    }
    
    public String draw(Curve curve) {
        return "Pencil drawing a " + curve.draw();
    }
}
```


```java
class Brush implements DrawingTool {
   Color color;

   public Brush(Color color) {
      this.color = color;
   }

   public Color getColor() {
      return color;
   }

   public void setColor(Color color) {
      this.color = color;
   }
   
    public String draw(Curve curve) {
        return "Brush drawing a " + curve.draw();
    }
}
```

### Key rules

**Reference — type relationships.**

An interface can extend one or more other interfaces using the keyword `extends`:

```java
interface A {
    void walk();
}

interface B {
    void run();
}

interface C { 
    void swim();
}

interface E extends A, B, C { 
    void talk();
}
```

```mermaid
classDiagram
    class A {
        <<interface>>
    }
    class B {
        <<interface>>
    }
    class C {
        <<interface>>
    }
    class E {
        <<interface>>
    }

    A <|-- E
    B <|-- E
    C <|-- E
```

A class can extend only one class and implement multiple interfaces:

```java
class A { }

interface B { }
interface C { }

class D extends A implements B, C { }
```

```mermaid
classDiagram
    class A

    class B {
        <<interface>>
    }

    class C {
        <<interface>>
    }

    class D

    A <|-- D
    B <|.. D
    C <|.. D

```

Multiple interfaces are often used in the standard library. A simplified excerpt of `String` shows some of its interfaces (not its complete Java 25 declaration):

```java
public final class String implements Serializable, Comparable<String>, CharSequence {
    // ...
}
```

### Methods with a body
#### Static methods

Interface fields are constants. Static methods provide utility behavior and are called on the declaring interface; they are not inherited as instance methods.

```java
interface DrawingTool {
    static final Color DEFAULT_COLOR = Color.BLACK;
    
    static boolean hasSameColor(DrawingTool a, DrawingTool b) {
        return a.getColor().equals(b.getColor());
    }
    // ...
}
```

To use a static method you just need to invoke it directly from an interface

```
DrawingTool.hasSameColor(pencil, brush);
```

The main purpose of interface static methods is to define utility functionality that is common for all classes implementing the interface. They help to avoid code duplication.

#### Default methods
A `default` method supplies an inheritable instance implementation in an interface. Static and private interface methods can also have bodies, but serve different roles.

Suppose many classes already implemented the `DrawingTool` interface. For example `pencil`, `pen`, `brush`, `fuzzybrush` etc. They all draw in different ways when `draw()` is called.

```java
interface DrawingTool {
    String draw(Curve curve);
    Color getColor();
    void setColor(Color color);
}
```

Then you decide that all tools should be always able to draw with a default color. That means:
* you need to add the `drawWithDefaultColor` method to the `DrawingTool` interface **and modify all implementing classes**
* **if implementing classes are a lot this could become very time-consuming!**. 

**The key motivation behind default methods in interfaces is supporting backward compatibility**. `default` methods provide a quicker solution in that you don't have to implement them in all classes.

```java
interface DrawingTool {
    static final Color DEFAULT_COLOR = Color.BLACK;
    
    String draw(Curve curve);
    Color getColor();
    void setColor(Color color);

    default String drawWithDefaultColor(Curve curve) {
        Color original = getColor();
        setColor(DEFAULT_COLOR);
        try {
            return draw(curve);
        } finally {
            setColor(original);
        }
    }
}
```


Although default methods are implemented, you cannot invoke them directly from an interface like `DrawingTool.drawWithDefaultColor()`. You still need to have an object of a class that implements the interface:

```
DrawingTool pencil = new Pencil(Color.RED);
pencil.drawWithDefaultColor(new Curve("line"));
```

The `finally` block restores color even if drawing fails. This temporarily mutates the tool and is **not a thread-safety guarantee**. A future API might accept color as an argument instead. Adding default methods can also create conflicts between interfaces: they are not an unconditional compatibility guarantee.

**Review:** an assistant omits `return` and restores the color only after a normal draw. Identify both the compilation problem and the failure-path bug. A `finally` block restores the color even if drawing throws an exception; restoration only after the call would be skipped on failure.

#### Private methods
Sometimes default methods are huge. To make it possible to decompose such methods, **Java allows declaring private methods inside an interface**:

```java
interface Feature {
    default void action() {
        String answer = subAction();
        System.out.println(answer);
    }

    private String subAction() {
        return "Default action";
    }
}
```
