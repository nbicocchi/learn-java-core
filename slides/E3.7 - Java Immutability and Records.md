## Immutability

An object is **immutable** when its observable state cannot change after construction.

* `final` fields help prevent reassignment but do not freeze referenced arrays, lists, or other mutable objects.
* A changed value is represented by another object rather than by mutating the original.
* `String` is a familiar immutable type. Its operations return a result without modifying the original; they do not necessarily allocate a new object every time.

**The class `Patient` is not immutable because it is possible to change any field of an object.**

```java
public class Patient {
    // field to store the patient's name
    public String name;
    
    // other stuff
    
}
```

```
Patient patient = new Patient();

patient.name = "Mary";
patient.name = "Alice";
```

### Immutable Classes
Passing immutable data reduces accidental changes through shared references. **It does not establish validity by itself**: construction must enforce the domain rules.
* Classes to simply hold data, such as database results, or information from a service.

For a simple immutable value class:
* prevent subclasses from adding incompatible mutable behavior, for example using a final class;
* **private, final field** for each piece of data
* defensively copy mutable inputs and outputs where needed;
* **getter** for each field (**setters** are useless in this case)
* **public constructor** with a corresponding argument for each field
* **equals method** that returns true for objects of the same class when all fields match
* **hashCode method** that returns the same value when all fields match
* **toString method** that includes the name of the class and the name of each field and its corresponding value

Equality, hashing, accessors, and string representation make a value class convenient; they are not themselves requirements for immutability. Avoid printing sensitive state in generated `toString` methods.

For example, we can create an immutable *Person* data class with a name and address:

```java
import java.util.Objects;

public final class Person {
    private final String name;
    private final String address;

    public Person(String name, String address) {
        this.name = name;
        this.address = address;
    }

    public String getName() {
        return name;
    }
    
    public String getAddress() {
        return address;
    }

    @Override
    public int hashCode() {
        return Objects.hash(name, address);
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) {
            return true;
        } else if (!(obj instanceof Person)) {
            return false;
        } else {
            Person other = (Person) obj;
            return Objects.equals(name, other.name)
              && Objects.equals(address, other.address);
        }
    }

    @Override
    public String toString() {
        return "Person [name=" + name + ", address=" + address + "]";
    }
}
```

### Records
Records are concise value-oriented data carriers with **final component fields**, not a guarantee of deep immutability. The compiler supplies a canonical constructor, component accessors, and implementations of `equals`, `hashCode`, and `toString` unless explicitly provided.

```java
public record Person (String name, String address) {}
```

The accessors are `name()` and `address()`, not `getName()` and `getAddress()`. The canonical constructor has the record's accessibility; it is public for this public record. Records are final and can implement interfaces, but cannot extend an application superclass.

### Defensive copies and compact constructors

**Predict:** if a record stores a caller's mutable list directly, can that caller change the record's observable contents?

```java
import java.util.List;
import java.util.Objects;

public record Team(String name, List<String> members) {
    public Team {
        Objects.requireNonNull(name);
        members = List.copyOf(members);
    }
}
```

The compact constructor validates and replaces the incoming list with an unmodifiable snapshot before fields are assigned. Here the elements are immutable strings, so this is sufficient for immutable list contents. If elements were mutable, a shallow snapshot would not freeze them.

**Review:** an assistant proposes `Collections.unmodifiableList(members)` instead. Test a later change through the caller's original list. A read-only view and an independent snapshot are different contracts.

> **Note:** array record components still use array identity in generated equality, not automatic element-wise comparison. Choose representations and custom methods deliberately when value equality must include array contents.

### Record patterns

**Note — reading modern Java 25 code:** record patterns deconstruct a record into its components. This feature has been final since Java 21; it does not require preview flags in Java 25.

```java
record Coordinates(int x, int y) {}

class DescribeCoordinates {
    static String describe(Object value) {
        return switch (value) {
            case Coordinates(int x, int y) -> "(" + x + ", " + y + ")";
            case null -> "No coordinates";
            default -> "Another type";
        };
    }
}
```

Here `int x` matches an `int` record component. This is not the preview feature that generalizes primitive patterns to other type-testing contexts. A record pattern reads components; it does not make their objects immutable.
