## Procedural vs Object-Oriented

### Procedural approach

* Data and functions are represented separately.
* Functions process data: _operation(data, params)_.
* Callers coordinate the operations and the state they act on.

For example, in C:

```c
#include <stdlib.h>

void init(int v[], int size) {
    for (int i = 0; i < size; i++) {
        v[i] = rand() % 100;
    }
}

void sort(int v[], int size) {
    for (int i = 0; i < size - 1; i++) {
        int changed = 0;
        for (int j = 0; j < size - i - 1; j++) {
            if (v[j] > v[j + 1]) {
                int tmp = v[j];
                v[j] = v[j + 1];
                v[j + 1] = tmp;
                changed = 1;
            }
        }
        if (!changed) break;
    }
}

int search(const int v[], int size, int value) {
    for (int i = 0; i < size; i++) {
        if (v[i] == value) {
            return i;
        }
    }
    return -1;
}

int main(void) {
    int v[100];
    int size = sizeof(v) / sizeof(v[0]);

    init(v, size);
    sort(v, size);
    int index = search(v, size, 10);
    (void) index;
    return 0;
}
```

Sorting is shown explicitly for teaching purposes. Production code should normally use an appropriate library implementation.

### Where complexity appears

![](images/intro-issues-procedural-approach.avif)

In this design:

* The array and its size are passed separately: callers must keep them consistent.
* Any code with access to the array can change its contents.
* Callers must know which operations are needed and in which order.

These are manageable responsibilities in a small program. They become harder to coordinate as more components use the same data.

**Procedural programming also supports modularity, data hiding, and reuse.** These limitations concern this design, not every procedural program.

The question is not “which paradigm always wins?” but **“where should responsibility for this data live?”**

### Object-oriented approach

* Related data and operations are grouped within a class.
* Objects provide services using their internal state: _object.operation(params)_.
* A public API controls how callers interact with that state.

![](images/intro-object-oriented-approach.avif)

```java
// App.java
public class App {
    public static void main(String[] args) {
        Vector vector = new Vector(100);
        vector.sort();
        int index = vector.search(10);
        System.out.println(index);
    }
}
```

```java
// Vector.java
import java.util.Random;

public final class Vector {
    private final int[] values;

    public Vector(int capacity) {
        if (capacity < 0) {
            throw new IllegalArgumentException("Capacity must be non-negative");
        }
        values = new int[capacity];
        init();
    }

    private void init() {
        Random random = new Random();
        for (int i = 0; i < values.length; i++) {
            values[i] = random.nextInt(100);
        }
    }

    public void sort() {
        for (int i = 0; i < values.length - 1; i++) {
            boolean changed = false;
            for (int j = 0; j < values.length - i - 1; j++) {
                if (values[j] > values[j + 1]) {
                    int tmp = values[j];
                    values[j] = values[j + 1];
                    values[j + 1] = tmp;
                    changed = true;
                }
            }
            if (!changed) break;
        }
    }

    public int search(int value) {
        for (int i = 0; i < values.length; i++) {
            if (values[i] == value) {
                return i;
            }
        }
        return -1;
    }
}
```

This is a teaching class, not `java.util.Vector`. It stores a fixed-size array; in application code, prefer standard collections when appropriate.

### What changed—and what did not?

* The object owns the array and derives its size from that array.
* Callers cannot directly replace or modify the internal array.
* The constructor establishes a usable initial state.
* The sorting and searching algorithms are unchanged: bubble sort and linear search.

**We changed ownership and responsibilities, not algorithmic complexity.** Search also does not require sorting first.

We switched from C to Java, but procedural organization is also possible in Java using static methods. The language switch is not what creates encapsulation.

**Read and discuss:**

1. Can `search` return different indices before and after sorting?
2. What should `search` return if the value is absent?
3. What happens with an empty vector?
4. Does `final int[]` prevent `sort()` from changing array elements?

The last answer is **no**: `final` prevents assigning a different array to the field, not modifying its contents.

### Review: does a getter preserve encapsulation?

An assistant proposes adding this method to `Vector`:

```java
public int[] getValues() {
    return values;
}
```

Now a caller can write:

```java
vector.getValues()[0] = -100;
```

1. Is the internal array still protected just because the field is `private final`?
2. We initialize values between 0 and 99. Should callers be allowed to bypass that choice?
3. If callers need a snapshot, could we return `values.clone()` instead?

Returning the original array exposes mutable internal state. A copy lets callers modify their snapshot without changing the object. Whether the range is a lasting invariant or just an initialization rule must be decided and documented.

### Reuse an algorithm without changing the API

Once the structural change is understood, replace the teaching implementation of `sort` with a standard library call:

```java
public void sort() {
    java.util.Arrays.sort(values);
}
```

The public operation still sorts the values in ascending order. Callers do not need to change.

**Separating these two steps matters:** moving an algorithm into a class changes organization; replacing it with a library implementation changes how the operation is performed.

## Object-Oriented Programming

OOP offers techniques for organizing software around objects with state, responsibilities, and interactions.

* **Abstraction** — expose a useful model without unnecessary details.
* **Encapsulation** — control access to state and implementation details.
* **Reuse** — build on existing functionality, including through composition and libraries.
* **Extensibility** — support new behavior while preserving existing contracts.

These benefits are design goals, not automatic consequences of using classes.

### Encapsulation

Encapsulation bundles state and operations within a boundary and controls how that state can be accessed.

* A class exposes a **public API**.
* It hides implementation details that callers should not depend on.
* Its operations should preserve the rules of a valid object state.
* Internal changes can leave callers unchanged **if the public contract is preserved**.

![](images/intro-encapsulation.avif)

For a point, callers need to know how to construct it and calculate a distance:

```text
Point(double x, double y)
double distance(Point other)
```

Here is a concrete implementation:

```java
// Point.java
public class Point {
    private final double x;
    private final double y;

    public Point(double x, double y) {
        this.x = x;
        this.y = y;
    }

    public double distance(Point other) {
        double dx = x - other.x;
        double dy = y - other.y;
        return Math.hypot(dx, dy);
    }
}
```

Assume non-null points and finite coordinates in the introductory examples. A production API should document its policy for nulls and special numeric values.

```java
Point a = new Point(0, 0);
Point b = new Point(3, 4);
System.out.println(a.distance(b)); // 5.0
```

The caller does not need direct access to `x` and `y`.

> Encapsulation supports abstraction: clients use meaningful operations rather than manipulate the representation.

It does not mean adding a getter and setter for every field. Unrestricted setters can undermine the boundary a class is supposed to provide.

### Inheritance

Inheritance allows a class to extend another class, reuse accessible behavior, and add or override behavior.

* The extending class is the **subclass**.
* The extended class is the **superclass**.
* Constructors are not inherited; a subclass constructor can invoke a superclass constructor with `super(...)`.
* Private fields are not directly accessible from subclass code.

Using the `Point` class above:

```java
// ColoredPoint.java
public class ColoredPoint extends Point {
    private final String color;

    public ColoredPoint(double x, double y, String color) {
        super(x, y);
        this.color = color;
    }

    public String getColor() {
        return color;
    }
}
```

```java
ColoredPoint red = new ColoredPoint(3, 4, "red");
Point origin = new Point(0, 0);

System.out.println(red.getColor());       // red
System.out.println(red.distance(origin)); // 5.0
```

`ColoredPoint` reuses `distance` without directly accessing the coordinates.

### Inheritance and reuse

Inheritance expresses an **IS-A** relationship: a `ColoredPoint` can be used where a `Point` is expected.

That relationship must also make sense behaviorally: the subclass should respect the superclass's contract.

**Inheritance is not the only way to reuse code.**

* `Vector` uses `Arrays.sort`: reuse through a library.
* A drawing application can contain points: reuse through **composition** (a HAS-A relationship).
* Functions can be reused without creating a hierarchy.

> Choose inheritance for a meaningful, substitutable specialization—not just to avoid duplicating a few lines.

### Polymorphism

Polymorphism allows code to use a common operation with different types.

Two mechanisms commonly discussed in introductory Java are **method overloading** and **method overriding**. Generics provide another form of polymorphism, introduced later.

#### Overloading versus overriding

| Mechanism | Question | Selection |
|---|---|---|
| **Overloading** | Which method signature applies? | At compile time, using argument expressions and their compile-time types |
| **Overriding** | Which implementation of that instance method runs? | At runtime, using the actual object type |

Overloading uses the same name with different parameter lists. For example, this convenience overload could be added to `Point`:

```java
public double distance(double x, double y) {
    return distance(new Point(x, y));
}

```

These calls use different signatures but calculate the same distance:

```java
Point point = new Point(3, 4);
point.distance(new Point(0, 0)); // 5.0
point.distance(0, 0);           // 5.0
```

Changing only the return type is not sufficient to overload a method. **Overriding is the mechanism we focus on next: it lets client code work with different implementations.**

#### (2) Dynamic (Run-time) Polymorphism

For an overridden instance method, the actual object type determines which implementation executes at runtime.

To illustrate this, add the following method to `Point`:

```java
public void draw() {
    System.out.println("Drawing a point");
}
```

Add this override to `ColoredPoint`:

```java
@Override
public void draw() {
    System.out.println("Drawing a " + color + " point");
}
```

A second subclass provides another implementation:

```java
// LabeledPoint.java
public class LabeledPoint extends Point {
    private final String label;

    public LabeledPoint(double x, double y, String label) {
        super(x, y);
        this.label = label;
    }

    @Override
    public void draw() {
        System.out.println("Drawing point " + label);
    }
}
```

The `draw` methods print descriptions for teaching purposes; they do not implement graphical rendering.

### One interface, different behavior

Here, “interface” means the common operations exposed by `Point`; a Java `interface` declaration is not required for this example.

```java
// DrawingApp.java
public class DrawingApp {
    public static void main(String[] args) {
        Point[] points = {
                new Point(0, 0),
                new ColoredPoint(3, 4, "red"),
                new LabeledPoint(5, 2, "A")
        };

        for (Point point : points) {
            point.draw();
        }
    }
}
```

Output:

```text
Drawing a point
Drawing a red point
Drawing point A
```

The loop does not need to inspect each concrete type.

An alternative would be a chain of checks:

```java
for (Point point : points) {
    if (point instanceof ColoredPoint) {
        // Handle colored points explicitly
    } else if (point instanceof LabeledPoint) {
        // Handle labeled points explicitly
    } else {
        // Handle ordinary points
    }
}
```

For this operation, overriding keeps type-specific behavior with the type that provides it. A new subclass can supply `draw()` without changing the original loop.

**This does not make every type check wrong.** Later we will compare inheritance, interfaces, composition, and pattern matching for different design needs.

### Read, predict, verify

Before running the drawing example:

1. Why can a `Point[]` contain a `ColoredPoint`?
2. The loop variable has type `Point`. Why does it execute `ColoredPoint.draw()`?
3. What happens if `ColoredPoint` does not override `draw()`?
4. Would adding a new subclass require changing the loop?

Then compile and run it to check your predictions.

## Using these ideas with AI-generated code

The same design questions apply whether code is written manually or generated:

| Concept | Review question |
|---|---|
| Abstraction | Does the API expose the operations callers actually need? |
| Encapsulation | Can callers bypass the rules or modify internal state unexpectedly? |
| Inheritance | Does the subclass preserve the superclass's contract? |
| Polymorphism | Can clients use the common operation without knowing each concrete type? |
| Reuse | Could an existing library or composition avoid unnecessary custom code? |

### Review: a faster search?

An assistant proposes replacing the linear search with:

```java
public int search(int value) {
    return java.util.Arrays.binarySearch(values, value);
}
```

The existing contract is:

* Search works before or after `sort()`.
* It returns the first matching index, or exactly `-1` if the value is absent.
* It does not modify the array.

Before accepting the change, review these cases:

| Values | Search | Existing result |
|---|---|---|
| `[8, 2, 5]` | `8` | `0`, even without sorting |
| `[2, 5, 8]` | `9` | Exactly `-1` |
| `[2, 2, 2]` | `2` | First matching index: `0` |

**Discuss:**

1. What precondition does `binarySearch` require?
2. What does it return for a missing value?
3. Does it guarantee the first matching index when duplicates exist?
4. Would sorting inside `search` preserve the existing behavior?

Check the [Java API contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Arrays.html#binarySearch(int%5B%5D,int)) and run `ExampleChecks`.

Binary search requires sorted input, uses negative insertion-point encoding for absent values, and does not guarantee the first duplicate. Sorting inside `search` would mutate the array and change the meaning of its indices.

> A faster algorithm can still be an incorrect replacement if it changes the contract.

Do not accept a design merely because it compiles or its explanation sounds convincing. Inspect it, check its contract, and test relevant behavior.

## Summary

* Growing software needs structure, regardless of how its code is produced.
* Functions remain useful; classes add boundaries around related state and behavior.
* Encapsulation controls access; abstraction exposes a useful model.
* Inheritance supports specialization, but composition and libraries also provide reuse.
* Polymorphism lets common client code work with different implementations.
* AI can help produce and explain code. Understanding and verification remain part of the developer's work.
