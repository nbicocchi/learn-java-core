# Java Exceptions

An exception is an object used to report an exceptional outcome and transfer control to a matching handler. It is thrown during execution; a compilation error is a different kind of failure.

All examples target **Java 25 without preview features** and build on methods, inheritance, and reference handling.

* **Core:** decide where to handle or propagate a failure, preserve useful diagnostics, and close owned resources.
* **Note:** custom exception design and suppressed exceptions.
* **Reference:** hierarchy and syntax patterns.

Put statement fragments inside `main` and method declarations inside a class. File examples need the relevant `java.io`, `java.nio.file`, `java.nio.charset`, or `java.util` imports. Blocks labeled as pseudocode explain control flow, not compilable Java.

## Why exceptions?
Imagine we need to write a method for loading a file in memory:

First approach (ignore error checking)
  * Short 
  * Readable 
  * Failure behavior is unspecified
  * **Not dependable**

```text
void loadFile()  {
  open file;
  determine file size;
  allocate memory;
  read file into memory;
  close file;
}

```

Second approach (error checking with [magic numbers](https://en.wikipedia.org/wiki/Magic_number_(programming)))
  * **Long**
  * **Obscure**
  * Can make failures explicit, if callers check the result
  * Cleanup still needs a policy

```text
int loadFile()  {
  open file;
  if (operationFailed) 
    return -1;
  
  determine file size; 
  if (operationFailed) 
    return -2;
  
  allocate memory; 
  if (operationFailed)
    return -3;
  
  read file into memory; 
  if (operationFailed)
    return -4;
  
  close file;
  if (operationFailed) 
    return -5;
  return 0;
}
```

Third approach (error checking with exceptions)
  * Reusable
  * Dependable
  * Readable

```text
void loadFile() {
  try {
      open file;
      determine file size;
      allocate memory; 
      read file into memory; 
      close file;
  } catch (fileOpenFailed) { 
      doSomething; 
  } catch(determineSizeFailed) {
    doSomething; 
  } catch (memoryAllocationFailed) { 
      doSomething; 
  } catch (readFailed) { 
      doSomething; 
  } catch (fileCloseFailed) { 
      doSomething; 
  }
}
```

These sketches illustrate reporting styles, not complete resource-safe implementations. Exceptions alone do not guarantee cleanup. The try-with-resources section below supplies that missing responsibility. A named result type can also be appropriate for expected outcomes; error codes are not intrinsically wrong.

## Exceptions examples

### ArithmeticException

Suppose you are writing a program that reads two integers from the standard input and then outputs the result of the integer division of the first number by the second one. Look at the code below.

```java
import java.util.Scanner;

public class ArithmeticExceptionDemo {

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);

        int a = scanner.nextInt();
        int b = scanner.nextInt();
        
        // ArithmeticException here if b == 0
        System.out.println(a / b); 
        System.out.println("finished");
    }
}
```

### NumberFormatException
Another situation to consider is when you are trying to convert a string into an integer number. If the string has an unsuitable format, the code will throw an exception.

The following program reads a line from the standard input and then outputs the number that follows it.

```java
import java.util.Scanner;

public class NumberFormatExceptionDemo {

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);
        String input = scanner.nextLine();

        // NumberFormatException here if user presses 121a
        int number = Integer.parseInt(input); 
        System.out.println(number + 1);
    }
}
```

### ArrayIndexOutOfBoundsException
This is a fairly common exception that occurs while working with arrays. It is caused by attempting to access a non-existent element of the array.

```java
int[] array = { 1, 2, 3 }; // an array of ints

int n1 = array[2];  // n1 is 3
int n2 = array[3];  // ArrayIndexOutOfBoundsException
int n3 = array[-1]; // ArrayIndexOutOfBoundsException
```

### NullPointerException (NPE)
`null` is a reference value identifying no object, not an uninitialized local variable. Dereferencing it or implicitly unboxing it can cause `NullPointerException`. Choose an explicit absence policy; checking null is not always preferable to rejecting an invalid argument at a boundary.

```java
String someString = null; // a reference type can be null

int size = someString.length(); // NullPointerException (NPE)
```

## Hierarchy of exceptions
Exceptions are considered objects of special classes organized into a class hierarchy. The following picture illustrates the simplified hierarchy of exceptions:

```text
Throwable
├─ Error (unchecked)
│   ├─ OutOfMemoryError
│   ├─ StackOverflowError
│   └─ ... (many more)
└─ Exception
    ├─ RuntimeException (unchecked)
    │   ├─ NullPointerException
    │   ├─ ArrayIndexOutOfBoundsException
    │   ├─ ArithmeticException
    │   └─ ... (many more)
    ├─ IOException (checked)
    │   └─ FileNotFoundException
    ├─ SQLException (checked)
    └─ ... (other checked exception classes)
```

The `Throwable` class has several important subclasses:

* **`Error`** – represents serious problems in the JVM, e.g., `OutOfMemoryError`, `StackOverflowError`.
* **`Exception`** – represents application-level events that can be handled, e.g., `SQLException`, `IOException`.
* **`RuntimeException`** – a subclass of `Exception` representing **unchecked exceptions**, e.g., `ArithmeticException`, `NumberFormatException`, `NullPointerException`.


### Checked exceptions

Checked exceptions are exception types other than `RuntimeException` and its subclasses, and other than the `Error` branch. The compiler requires eligible checked failures to be caught or declared. Whether a failure is recoverable depends on the caller and context, not just on this classification.

With checked exceptions, the compiler forces the programmer to make a choice:
  
**Handle the exception** using a `try-catch` block:
```java
public static void displayFile() {
    try {
        String text = java.nio.file.Files.readString(java.nio.file.Path.of("file.txt"));
        System.out.println(text);
    } catch (java.io.IOException e) {
        System.err.println("Cannot display file.txt: " + e.getMessage());
    }
}
```

**Propagate it** by declaring `throws` in the calling method.
```java
public static String readTextFromFile() throws java.io.IOException {
    return java.nio.file.Files.readString(java.nio.file.Path.of("file.txt"));
}
```

The first method is a console boundary that reports failure; the second leaves the decision to its caller. Returning an empty string after an I/O failure would make “empty file” indistinguishable from “could not read.” `Files.readString` owns and closes the underlying file operation.

### Unchecked Exceptions

Java introduced **unchecked exceptions** to address situations where **forcing the programmer to declare or handle every possible error would be cumbersome or unnecessary**.

```java
int[] array = { 1, 2, 3 }; // an array of ints

int n2 = array[3];  // ArrayIndexOutOfBoundsException is unchecked
```

`RuntimeException` and its subclasses are unchecked exceptions; `Error` and its subclasses are also unchecked throwable types. The compiler does not require catching or declaring them. That does not make them safe to ignore or imply that catching every `Throwable` is sensible.

```java
public static Long convertStringToLong(String str) {
    return Long.parseLong(str); // may throw NumberFormatException
}
```
This code **compiles successfully** without using the `throws` keyword because `NumberFormatException` is **unchecked**.

## Throwing exceptions
### The throw keyword
Any object of the  `Throwable`  class and all its subclasses can be thrown using the **throw** statement. 

```java
public class Main {
    public static void main(String[] args) {
        throw new RuntimeException("Something's bad.");
    }
}
```

With no handler in this example, the main thread terminates and the default uncaught-exception handling prints a stack trace:

```text
Exception in thread "main" java.lang.RuntimeException: Something's bad.
	at Main.main(Main.java:3)
```

### Throwing checked exceptions

```java
public static String readTextFromFile(String path) throws java.io.IOException {
    if (path.isBlank()) {
        throw new IllegalArgumentException("Blank path");
    }
    return java.nio.file.Files.readString(java.nio.file.Path.of(path));
}
```

The `throws` keyword following the method parameters is required since an `IOException` is a checked exception. Otherwise, the code won't compile.

If a method throws two or more checked exceptions, they must be separated by a comma in the declaration:

```text
public static void method() throws ExceptionType1, ExceptionType2, ExceptionType3 {
  // ...
}
```

If a method is declared as throwing an exception, it can also throw any subclass of the specified exception. In the example below, `FileNotFoundException` does not require a specific annotation because it is a subclass of `IOException`:

```java
public static String readLine(String filename) throws IOException {
  try (BufferedReader reader = new BufferedReader(new FileReader(filename))) {
    return reader.readLine(); // null at end-of-file; IOException on read failure
  }
}
```

### Throwing unchecked exceptions
The  `Account`  class contains the method called  `deposit`, that adds the specified amount to the current balance. If the amount is not positive or exceeds the limit, the method throws an `IllegalArgumentException`.

```java
class Account {

    private long balance = 0;

    public void deposit(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Incorrect sum " + amount);
        }

        if (amount >= 100_000_000L) {
            throw new IllegalArgumentException("Too large amount");
        }

        balance = Math.addExact(balance, amount);
    }
    
    // ...
}
```

If a method throws an unchecked exception such as `IllegalArgumentException`, the keyword `throws` is not required in the method declaration.

```java
public class AccountUtils {

  /**
   * Tries to deposit a given amount into the account.
   * Prints a message whether the deposit succeeded or failed.
   */
  public static void safeDeposit(Account account, long amount) {
    try {
      account.deposit(amount);
      System.out.println("Deposit successful: " + amount);
    } catch (IllegalArgumentException e) {
      System.out.println("Deposit failed: " + e.getMessage());
    }
  }

  public static void main(String[] args) {
    Account myAccount = new Account();

    // Test deposits
    safeDeposit(myAccount, 1000);          // valid
    safeDeposit(myAccount, -50);           // invalid: negative
    safeDeposit(myAccount, 200_000_000L);  // invalid: too large
  }
}
```

### When to throw an exception?
Technically, throwing an exception is a rather straightforward task. But the question is, when do you need to do this? The answer is not always obvious. 

Throw when the method cannot fulfill its contract and its API represents that failure with an exception. Broken preconditions are one case; external I/O failures, timeouts, and unavailable services can also occur with valid arguments.

* A date parser can throw `DateTimeParseException` for input that does not match its supported date format.
* A method reading a non-existing file throws a `FileNotFoundException`.

Choose a relevant standard type, such as `IllegalArgumentException`, rather than a generic `Exception` when possible. There is no standard `java.lang.InvalidArgumentException`. Expected absence may instead use a documented empty result or `Optional`; do not use exceptions as routine loop control.

## Handling exceptions

### The try-catch statement

```
try {
    // code that may throw an exception
} catch (Exception e) {
    // code for handling the exception
}
```

The `try` block is used to wrap the code that may throw an exception.

The `catch` block is a handler for the specified type of exception and all of its subclasses. This block is executed when an exception of the corresponding type occurs in the `try` block. 

```java
public static void main(String[] args) {
  System.out.println("before the try-catch block"); // it will be printed

  try {
    System.out.println("inside the try block before an exception"); // it will be printed
    System.out.println(2 / 0); // it throws ArithmeticException
    System.out.println("inside the try block after the exception"); // it won't be printed
  } catch (ArithmeticException e) {
    System.out.println("Division by zero!"); // it will be printed
  }
  
  System.out.println("after the try-catch block"); // it will be printed

}

```

The output:

```text
before the try-catch block
inside the try block before an exception
Division by zero!
after the try-catch block
```

The program does not print `"inside the try block after the exception"` since the `ArithmeticException` aborted the normal flow of the execution. Instead, it executes the print statement in the `catch` block. After completion of the `catch` block, the program executes the next statement (printing `"after the try-catch block"`) without returning to the `try` block again.


### Catching multiple exceptions
Java supports the use of several handlers inside the same `try` block.

```
try {
    // code that throws exceptions
} catch (IOException e) {
    // handling the IOException and its subclasses
} catch (Exception e) {
    // handling the Exception and its subclasses
}
```

The more specialized handlers (like `IOException`) must be written before the more general ones (like `Exception`).

Catch only failures that this layer can meaningfully handle, translate, or report. A broad catch that substitutes a plausible default may hide a bug.

### Read a stack trace and preserve the cause

Start with the exception type and message, locate the relevant application frame, and follow any `Caused by` chain. Source line numbers depend on the actual file.

```java
public static int parseCount(String input) {
    try {
        return Integer.parseInt(input);
    } catch (NumberFormatException cause) {
        throw new IllegalArgumentException("Invalid count: " + input, cause);
    }
}
```

This example adds domain context while preserving the original cause. In production, avoid putting secrets or sensitive payloads in exception messages. Logging and rethrowing at every layer can duplicate the same failure many times.


## Custom exceptions
To create a custom exception you need to extend the `Exception` (checked) or `RuntimeException` (unchecked) classes.

```java
public class MalformedRequestException extends Exception {
  public MalformedRequestException() {
  }

  public MalformedRequestException(String message) {
    super(message);
  }

  public MalformedRequestException(String message, Throwable cause) {
    super(message, cause);
  }

  public MalformedRequestException(Throwable cause) {
    super(cause);
  }

  public MalformedRequestException(String message, Throwable cause, boolean enableSuppression, boolean writableStackTrace) {
    super(message, cause, enableSuppression, writableStackTrace);
  }
}

```

In the example above, a new class of exceptions is declared. It is a checked exception because it extends the `Exception` class. The declared class has five constructors for creating instances, and they call the corresponding constructor of the base class. They can be all auto-generated in IntelliJ.

Now, we can throw an instance of the class:

```java
public static void someMethod() throws MalformedRequestException {
    throw new MalformedRequestException("Something bad");
}
```

### Best practices for custom exceptions
* In general, **it is advisable to use standard exceptions whenever possible**:
  - Standard exceptions are widely known by other programmers. One can understand the type of problem just by looking at the name of the exception. 
  - By opting for standard exceptions, you follow the reusability principle. It makes your code clearer and more professional.

## Closing resources

When a file is opened, the JVM requests a **file descriptor** from the OS, which is a limited resource. If an exception occurs before `close()` is called, the file descriptor may not be released, potentially causing **resource leaks**. Properly closing streams ensures that system resources are freed for reuse.


```
Reader reader = null;

try {
    // code which may throw an exception
    reader = new FileReader("file.txt");
    
    reader.close();
} catch (IOException e) {
    // do something
}
```

The older **try-finally** pattern places cleanup on both normal and exceptional control-flow paths. `finally` is not literally guaranteed under every circumstance, such as abrupt JVM termination. Prefer try-with-resources for owned `AutoCloseable` resources.

```
Reader reader = null;

try {
    // code which may throw an exception
    reader = new FileReader("file.txt");
} catch (IOException e) {
    // do something
} finally {
    if (reader != null) {
        reader.close(); // Still needs an IOException policy; can mask an earlier failure.
    }
}
```



### try-with-resources
**try-with-resources** has two parts:

* **Round brackets** – declare and create one or more resources (e.g., input streams).
* **Curly brackets** – contain the code that uses these resources.

The `close()` method is automatically invoked for successfully initialized non-null resources, in reverse declaration order. A resource must implement `AutoCloseable`; closure itself can fail.



```
try (Reader reader = new FileReader("file.txt")) {
    // some code
}
```

```
try (Reader reader1 = new FileReader("file1.txt");
     Reader reader2 = new FileReader("file2.txt")) {
    // some code
}
```

**Core:** use try-with-resources for resources this scope owns. Do not close a borrowed stream merely because a helper can wrap it; for example, closing a scanner over `System.in` closes that shared input source.

```
try (Scanner scanner = new Scanner(new File("file.txt"))) {
    int first = scanner.nextInt();
    int second = scanner.nextInt();
    System.out.println("arguments: " + first + " " + second);
}
```

> **Note:** if the body and cleanup both throw, the body failure remains primary and cleanup failures are suppressed exceptions, available through `getSuppressed()`. This preserves information more reliably than a naive finally block.

## Exceptions and loops
For errors affecting a single iteration (or items of a collection!), the try-catch blocks is nested in the loop. In case of exception the execution goes to the catch block and then proceed with the next iteration.

```
while (something) {
  try {
    // potential exceptions
  } catch (Exception e) {
    //  discard iteration (continues the loop)
  }
}
```

For errors compromising the whole loop, the loop is nested within the try block. In case of exception the execution goes to the catch block, thus exiting the loop.

```
try {
  while (something) {
    //  potential exceptions
  }
} catch (Exception e) {
  // discard whole loop
}
```

## Read, predict, verify

**Predict:** if parsing the second item throws, does the next iteration run when the catch is outside the loop? Move the catch inside and explain which failure policy changed.

**Debugger activity:** set an exception breakpoint for `NumberFormatException`, run `parseCount("12x")`, and inspect the original failure and translated cause. Check the stack trace before accepting a proposed fix.

**Exit review:** an assistant wraps a file operation in `catch (Exception e) { return ""; }`. Identify the hidden outcomes, the appropriate handling layer, and a test that distinguishes an empty file from a missing one.
