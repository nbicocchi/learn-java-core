# E1.1 — From Functions to Classes

## Java in the real world

Java is used in several application areas:

* **Enterprise systems:** Java, often with Spring Boot, is widely used for APIs and services. It powers major backend systems at **Netflix, LinkedIn, Amazon, and Uber**, alongside other languages.
* **Event streaming:** **Apache Kafka**, originally developed at LinkedIn, is a widely used platform for event streams, built primarily with Java and Scala.
* **Applications and developer tools:** **JetBrains software**, and **Jenkins** are familiar examples of software built with Java.
* **Android and the JVM ecosystem:** Java remains relevant through existing Android code and interoperability with Kotlin. Android has its own runtime; on the JVM, Java also shares an ecosystem with Kotlin, Scala, and other languages.

Beyond these applications, **Java is one of the most established expressions of class-based object-oriented programming**. Its language features, standard libraries, and ecosystem provide a rich foundation for studying how to organize software around objects, responsibilities, and clear boundaries.

**That is why we use Java in this course:** not just to learn a widely used language, but to practice structured object-oriented design. Using Java does not automatically produce good design; learning to make those design choices is our goal.

## Why this course?

### The program works. Then something changes.

Imagine a program that stores a student's marks and calculates their average. It works.

Then the requirements evolve:

1. **Validate marks:** only values from 0 to 30 are accepted. A value such as 35 must be rejected, not included in the average.
2. **Calculate a weighted average:** an exam counts twice as much as a short quiz. Adding all marks and dividing by their number is no longer the correct calculation.
3. **Import marks from a file:** another developer adds an alternative to manual entry. Imported marks must follow the same validation rules as marks entered manually.

* Where should the validation rules live?
* Does every way of entering a mark apply the same rules?
* How many parts must change when the calculation changes?
* How do we know that existing behavior still works?

Each calculation may be simple. **Keeping the whole program consistent as it changes is the harder problem.**

### From solving a problem to maintaining a program

Knowing variables, loops, and functions lets us express algorithms. As programs grow, we also need to decide:

* Which part is responsible for each rule?
* What does one part need to know about another?
* What can change independently?
* How can we check each part without understanding everything at once?

**This course is about making that transition:** from writing a working computation to organizing software that we and others can understand, verify, and modify.

Objects and functional techniques offer different tools for doing this. First, let us look at why the problem matters.

* Does the program satisfy its requirements?

## From algorithms to responsibilities

### A small program is easy to hold in your head

Suppose a program stores numbers, sorts them, and searches for a value.

In a procedural organization, functions operate on data supplied by the caller:

```text
init(values, size)
sort(values, size)
index = search(values, size, 10)
```

These are schematic calls, not a complete program. The important point is the organization: **data and the functions that operate on it are represented separately**.

For a small program, this can be clear and effective.

### Where complexity appears

![](images/intro-issues-procedural-approach.avif)

In this design:

* The array and its size are passed separately: callers must keep them consistent.
* Any code with access to the array can change its contents.
* Callers must know which operations are needed and in which order.

These are manageable responsibilities in a small program. They become harder to coordinate as more components use the same data.

**Procedural programming also supports modularity, data hiding, and reuse.** These limitations concern this design, not every procedural program.

The question is not “which paradigm always wins?” but **“where should responsibility for this data live?”**

### The object-oriented idea

Instead of making every caller coordinate the data, give that responsibility to an object:

```text
vector = a new Vector containing 100 numbers
vector.sort()
index = vector.search(10)
```

![](images/intro-object-oriented-approach.avif)

The object keeps track of its own data and offers operations through which other parts of the program can use it.

* **State:** the numbers it currently contains.
* **Operations:** sorting and searching those numbers.
* **Responsibility:** keeping the representation consistent and controlling how it is used.

Callers ask the object to do something, rather than manage all its internal details themselves.

### Class and object: just enough vocabulary

A **class** describes a kind of object: the state it holds and the operations it offers.

An **object** is a particular instance, with its own state.

Two vectors can offer the same operations while containing different numbers. Sorting one should not change the other when they own independent data.

For this conceptual example, focus on **who is responsible for what**, rather than the syntax for declaring a class.

### What changed—and what did not?

* The object owns the numbers and keeps track of their size.
* Callers use a small set of operations instead of manipulating the internal representation directly.
* Responsibility for managing that representation is concentrated in one place.
* Sorting and searching still need algorithms: putting them in a class does not automatically make them faster.

**We changed ownership and responsibilities, not algorithmic complexity.** Searching does not inherently require sorting first; that depends on the chosen algorithm.

The difference is not simply C versus Java: procedural organization is possible in Java too.

## Why this helps with change

### Encapsulation: a boundary around a responsibility

**Encapsulation** groups state and operations within a boundary and controls how that state can be accessed.

![](images/intro-encapsulation.avif)

For example, callers of our vector should not need to update a separate size whenever its representation changes.

The object handles those details. Its public operations form an **API**: the ways other code is allowed to interact with it.

The benefit is not simply “hiding variables”. It is **reducing the number of places that must know and preserve the same rules**.

### Abstraction: use an operation without knowing its implementation

A point can offer an operation for calculating the distance to another point:

```java
Point a = new Point(0, 0);
Point b = new Point(3, 4);
System.out.println(a.distance(b)); // 5.0
```

This is a preview of Java syntax, not an exercise in defining a class. Assume a `Point` class that keeps its coordinates private and provides `distance`.

The caller knows what a point represents and what distance means. It does not need direct access to the coordinates or the calculation formula.

**Abstraction** exposes a useful model without requiring callers to know every implementation detail. Encapsulation helps maintain that separation.

### Change the implementation, preserve the promise

Suppose we replace our vector’s handwritten sorting algorithm with a standard library implementation.

Callers still ask:

```text
vector.sort()
```

If the operation preserves its promised behavior, callers do not need to change.

That promise is a **contract**: what an operation requires and what it guarantees. For example, `sort` leaves the same numbers in ascending order.

**A boundary is useful when it lets us change one part without making unrelated parts change too.**

### A faster implementation can still be the wrong change

Suppose `search` promises to work even before sorting and to return the first matching index, or `-1` when the value is absent.

An AI assistant proposes replacing a linear search with binary search.

Before accepting, ask:

* Does the new algorithm require sorted input?
* Does it preserve the promised results for duplicates and missing values?
* Would sorting first change the data or the meaning of its indices?

**Hiding an implementation does not make every replacement correct**.

### Objects are not a guarantee of good design

Adding a class around existing code is not enough.

* If every caller can freely modify the internal data, the same coordination problems remain.
* If one object does everything, it can still be difficult to understand and change.
* If a change requires inspecting the whole program, the boundaries may not be helping.

> We introduce objects to limit how much we must know at once and how many parts must change together—not to write more code.

## Another approach: functional programming

### Focus on transformations rather than changing shared state

The functional approach emphasizes **composing functions that transform values**, favoring immutable data and limiting or making effects explicit.

* **Immutable data** is not modified after it is created.
* An **effect** is an interaction beyond returning a result, such as changing shared data or printing output.
* A **pure function** depends only on its inputs and produces a result without such effects.

For a qualitative contrast:

```text
Change an existing vector:
    vector.sort()

Produce a sorted result while keeping the original:
    sortedValues = sortedCopy(values)
```

The second operation illustrates a functional idea: reason about an input and a result without having to track a modification to the original data. One function alone does not make an entire program functional.

### Different ways to manage complexity

| Approach | Main emphasis |
|---|---|
| **Procedural** | Organize procedures that operate on data. |
| **Object-oriented** | Assign responsibilities to objects that encapsulate state and operations. |
| **Functional** | Compose transformations of values, favoring immutability and controlled effects. |

Objects help us ask: **“Who is responsible for this state and its rules?”**

Functional programming helps us ask: **“Can I express this computation as transformations without changing shared state?”**

These are not successive stages where one makes the others obsolete. They offer different tools and trade-offs for the same broad challenge: making software easier to reason about and change.

### Complementary, not incompatible

An object can be immutable. A method can compute a result without changing anything. An object-oriented application can use functional transformations internally.

Real applications also need effects: reading files, displaying results, or storing data. The question is how to organize and control them, not pretend they do not exist.

**Java allows us to combine these approaches:** objects can define responsibilities and boundaries while functions express transformations within those boundaries.
