# E3.10 — SOLID Principles

SOLID groups five design principles intended to make software easier to understand and change. Robert C. Martin helped formulate and popularize these principles; the underlying ideas have multiple origins.

> SOLID is a set of design heuristics, not a requirement to create an interface for every class or to maximize the number of types.

The bank-account, bird, and report examples below retain the original progression. Compile each section's types separately; some sections introduce alternative designs. Method fragments belong inside their indicated class.

## Single responsibility principle (SRP)

A module should have **one coherent reason to change**: changes driven by different concerns or stakeholders should not be unnecessarily coupled.

A class can have several related methods and still have one responsibility.

Consider a bank account that manages its balance, writes SQL, and sends SMS messages:

```text
BankAccount
 ├─ deposit / withdraw / calculateInterest
 ├─ saveBankAccountDetails
 └─ sendSmsNotification
```

An interest rule, a database schema, and a messaging provider can change independently. Keeping all three in one class creates unrelated edit paths.

### Separate state rules from infrastructure

This balance example uses **integer cents in one assumed currency**, with no interest, fees, or concurrency. It is not a full banking model.

```java
public final class BankAccount {
    private long balance;

    public BankAccount(long initialBalance) {
        if (initialBalance < 0) {
            throw new IllegalArgumentException("Negative initial balance");
        }
        balance = initialBalance;
    }

    public long getBalance() {
        return balance;
    }

    public void deposit(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Deposit must be positive");
        }
        balance = Math.addExact(balance, amount);
    }

    public void withdraw(long amount) {
        if (amount <= 0 || amount > balance) {
            throw new IllegalArgumentException("Invalid withdrawal");
        }
        balance -= amount;
    }
}
```

Persistence and notification can be separate collaborators:

```java
class SQLBankAccountRepository {
    public void save(BankAccount account) {
        // Infrastructure boundary: database implementation omitted.
    }
}

class NotificationService {
    public void sendSmsNotification(BankAccount account, String message) {
        // Infrastructure boundary: SMS implementation omitted.
    }
}

class BankAccountService {
    private final SQLBankAccountRepository repository;
    private final NotificationService notifications;

    public BankAccountService(SQLBankAccountRepository repository,
                              NotificationService notifications) {
        this.repository = java.util.Objects.requireNonNull(repository);
        this.notifications = java.util.Objects.requireNonNull(notifications);
    }

    public void deposit(BankAccount account, long amount) {
        account.deposit(amount);
        repository.save(account);
        notifications.sendSmsNotification(account, "Deposit: " + amount);
    }
}
```

The empty infrastructure bodies mark omitted integrations, not working database or SMS code. The service coordinates the workflow while the account owns balance rules.

**Review:** if saving succeeds but notification fails, should the deposit be repeated? Separating classes does not by itself provide transactions, idempotency, or a failure policy.

## Open closed principle (OCP)

Software can be **open to a selected kind of extension without requiring changes throughout existing client code**.

This does not mean “never modify existing code.” Choose extension points for changes that are plausible, not every imaginable future feature.

The original account example calculates interest by checking account-type strings. A new interest rule would require another branch. One alternative is to make that rule a collaborator:

```java
interface InterestPolicy {
    double calculate(double balance);
}

final class SavingsInterest implements InterestPolicy {
    @Override
    public double calculate(double balance) {
        return balance * 0.03;
    }
}

final class CheckingInterest implements InterestPolicy {
    @Override
    public double calculate(double balance) {
        return balance * 0.01;
    }
}

final class FixedDepositInterest implements InterestPolicy {
    @Override
    public double calculate(double balance) {
        return balance * 0.05;
    }
}

final class InterestService {
    public double calculate(double balance, InterestPolicy policy) {
        if (!Double.isFinite(balance) || balance < 0) {
            throw new IllegalArgumentException("Invalid balance");
        }
        return policy.calculate(balance);
    }
}
```

This independent example uses `double` to show varying formulas, not production monetary arithmetic. Policy implementations assume non-negative finite balances; clients supply a non-null policy. A real implementation needs units, periods, and rounding rules.

Adding a policy need not change `InterestService`. Configuration or construction code still chooses the policy.

> **Note:** a short switch over a stable, closed set may be clearer than several strategy classes. OCP is not a ban on switches or a mandate to replace simple constants with hierarchies.

## Liskov Substitution Principle (LSP)

A subtype should be usable wherever its supertype is expected **without breaking the client's documented expectations**.

Matching signatures is necessary, but not sufficient. Preconditions, postconditions, and invariants matter too.

Suppose `Bird.fly()` promises that a valid call performs flight. A `Penguin` override that always throws breaks that promise even if the code compiles.

Instead, model the capability only where it applies:

```java
class Bird {
    public void eat() {
        System.out.println("Eating");
    }
}

interface Flying {
    void fly();
}

final class Parrot extends Bird implements Flying {
    @Override
    public void fly() {
        System.out.println("Flying");
    }
}

final class Penguin extends Bird {
}
```

**Predict:** which objects can be supplied to a method taking `Bird`? Which can be supplied to one taking `Flying`?

<details>
<summary>Check your prediction</summary>

Both objects satisfy `Bird`; only `Parrot` satisfies `Flying`. We corrected the advertised capability rather than adding a runtime “unsupported” branch to every caller.

</details>

**Review:** a subclass accepts fewer valid input values than the superclass contract. Does its `@Override` annotation establish substitutability? Design a contract test that runs against both implementations.

## Interface segregation principle (ISP)

**Clients should not be forced to depend on operations they do not need.** Organize contracts around coherent client roles.

If a loan account cannot offer ordinary withdrawal, forcing it to implement a broad account interface may produce a dummy method, a silent no-op, or an unexpected exception.

An alternative is to expose separate capabilities:

```java
interface BalanceView {
    long getBalance();
}

interface Depositable {
    void deposit(long amount);
}

interface Withdrawable {
    void withdraw(long amount);
}

final class CashMachine {
    public void withdraw(Withdrawable account, long amount) {
        account.withdraw(amount);
    }
}
```

An ordinary account can implement all three; another product can implement only its relevant capabilities. The cash machine depends only on withdrawal.

**Activity:** adapt the earlier `BankAccount` to implement these interfaces without changing its balance rules. Then identify whether a particular client actually benefits from the split.

> **Note:** splitting every method into its own interface can create needless indirection. Segregate by client needs, not by an arbitrary maximum method count.

## Dependency inversion principle (DIP)

High-level policy should not be tightly coupled to low-level implementation details. Both can depend on an abstraction shaped by the policy's needs.

In the report example, a service that constructs both PDF and HTML generators must know each implementation and its setup.

Introduce a common contract and supply the implementation from outside:

```java
interface ReportGenerator {
    String generateReport();
}

final class PDFReportGenerator implements ReportGenerator {
    @Override
    public String generateReport() {
        return "PDF report description";
    }
}

final class HTMLReportGenerator implements ReportGenerator {
    @Override
    public String generateReport() {
        return "HTML report description";
    }
}

final class ReportService {
    private final ReportGenerator generator;

    public ReportService(ReportGenerator generator) {
        this.generator = java.util.Objects.requireNonNull(generator);
    }

    public String generateReport() {
        return generator.generateReport();
    }
}
```

These generators return descriptions, not actual PDF or HTML documents. The example isolates the dependency boundary.

Client construction can be explicit:

```java
ReportService service = new ReportService(new HTMLReportGenerator());
System.out.println(service.generateReport());
```

Constructor injection does not require a framework. A test can supply `() -> "test report"` and verify delegation without a document renderer.

**Dependency injection is a technique; dependency inversion is a design principle.** Injecting a concrete, infrastructure-specific dependency does not automatically invert the architectural dependency.
